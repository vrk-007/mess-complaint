# VNIT Mess & Canteen Complaint System - Project Context

## Project Overview
This project is an automated Mess & Canteen Complaint & Feedback Management Portal for VNIT students, mess admins, and institute superadmins.

- **Primary Goal:** Enable students to submit real-time, authenticated food and hygiene complaints with photo evidence (verified via QR code tokens generated at messes), provide canteen item ratings, and allow mess admins & superadmins to track, escalate, remark upon, and approve resolutions.

---

## Tech Stack
- **Framework:** Next.js 16 (App Router, Server Actions, React 19)
- **Database & ORM:** PostgreSQL (Supabase / Direct URL) with Prisma ORM 5.22
- **Authentication:** NextAuth.js v5 (Auth.js beta), Database Sessions via `@auth/prisma-adapter`
- **File Storage:** Supabase Storage (public bucket for complaint photo evidence)
- **Styling:** Tailwind CSS v4, custom responsive UI
- **Email & Alerts:** Nodemailer (SMTP) / Resend for transactional email notifications
- **QR Tokens:** `html5-qrcode` (scanner) and `qrcode.react` (generator)

---

## Key Roles & Access Control
- `STUDENT`: Can view student dashboard (`/dashboard`), submit complaints via QR token (`/`), rate VNIT Canteen items (`/rate`), and edit profile/hostel/mess (`/onboarding`).
- `ADMIN`: Hostel/Mess Admin (`/admin`). Generates single-use QR tokens, views complaints for their assigned mess, submits remarks, forwards severe issues to SuperAdmin, and submits resolution requests.
- `SUPER_ADMIN`: Institute SuperAdmin (`/superadmin`). Cross-mess analytics, inspects system stats, reviews escalated complaints, adds superadmin remarks, and approves pending resolutions.
- **Special Venue ("VNIT Canteen"):** Canteen complaints/ratings operate under special filtering. In the superadmin view, system/superadmin stats are hidden when "VNIT Canteen" is selected.

## Domain Workflows & Business Rules

### 1. Complaint Submission & QR Verification
- To prevent spam, filing a mess complaint requires scanning a valid, `ACTIVE` single-use QR token generated by that mess's admin (`ComplaintToken`).
- When submitted, token status changes from `ACTIVE` to `USED`.
- Photo evidence is compressed client-side, uploaded to Supabase Storage, and stored as `imageUrl`.
- Email notification is triggered to the mess admin via `lib/email.ts`.

### 2. Escalation & Remarks Workflow
- Admins can add notes (`adminRemark`, `remarkBy`, `remarkAt`).
- Admins can escalate severe issues to SuperAdmin (`isForwarded = true`, `forwardedBy`, `forwardNote`).
- SuperAdmins can review escalated complaints and add remarks.

### 3. Resolution & Approval Workflow
- If a complaint was NOT escalated: Admin marks it resolved directly (`resolved = true`).
- If a complaint WAS escalated: When an Admin submits a resolution, it enters `pendingApproval = true` with `resolutionRemark` and `resolvedBy`.
- The SuperAdmin (or escalating admin) must review and approve the resolution (`approvedBy`, `approvedAt`), which transitions `pendingApproval = false` and `resolved = true`.

## Development Guidelines
- Always use **Server Actions** (`'use server'`) inside `app/actions/` for database mutations.
- Always verify authentication (`await auth()`) and authorize roles inside Server Actions before mutating data.
- Run database migrations / push via `npx prisma db push` or `npx prisma generate` when schema changes.
- Email alerts should execute non-blockingly or gracefully handle network/SMTP failures so complaints/resolutions still succeed.
